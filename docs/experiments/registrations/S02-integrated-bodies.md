## Contract and hypotheses

Prepare an immutable plan from one simplification rule with removed heads `take(Pattern, Output), token()`. Output is a distinct head variable; Pattern may contain nested constructors and repeated variables. Support True, Fail, conjunction, arbitrary finite-tree equations, and posted constraints in the body. Body-only variables are fresh for each application and shared within that application's body. Posted take/2 and token/0 occurrences participate in subsequent execution; other predicate/arity combinations remain observable residual facts.

Retain the source evaluator's body barrier: process body goals in order and complete their equations before the next body goal; select no consuming application until the whole body has completed. Computing readiness earlier is permitted, but consuming a token early is not. Validate an example where an early-ready emitted request would steal a token from an older request that becomes ready later in the same body.

H1: source-derived constructor equations and subsequent consuming applications can execute directly on the same handle graph without exporting syntax terms to a separate body executor. H2: immutable preparation can be reused across queries with changed arguments and aliases without leaking query state. H3: body ordering, fresh identities and residual ownership add necessary responsibilities; endpoint/filtered/indexed subscription gains alone cannot decide their total cost.

This is an experimental source fragment. Or bodies, kept heads, guards, arbitrary head combinations and general multiple-rule selection are not implemented by this gate and must be rejected explicitly rather than interpreted through a fallback. No language restriction is adopted.
