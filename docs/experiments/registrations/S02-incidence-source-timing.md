# Incidence buckets through complete source execution

Registered before experimental runs. T072, third package since portfolio review.

**Question:** do vector incidence buckets improve lifecycle time after equality repair and consuming source execution, including high-degree movement? Keep ordered sets and the independent compiled path as controls. No default change is authorized by a component allocation gain alone.

Extend the existing readiness runner with broad sources: distinct unknowns occur repeatedly in edge columns and constructor children, bind rules merge them onto `a`, then edge consumption emits one receipt per source occurrence. Constructor facts may coalesce; receipts must retain source multiplicity. Validate all complete answers against both the independent scalar evaluator and an analytical multiset. Alternate width and duplicate multiplicity between two queries reusing prepared rules. Reverse insertion and reverse binding order are independent parameters. Cancellation occurs after admission, followed by disposal; the separate qualified store test already checks clone independence.

First qualify widths8/64/128, both insertion orders and both binding orders, full/batch256/compiled, ordered-set and vector ordinary builds:72 processes of two queries. Bound each process to60seconds CPU/wall and1GiB address space, with100,000 advances per query. Builds precede bounds. Any cutoff or mismatch requires investigation before comparative timing; the scalar oracle also must finish.

Then run a bounded timing pilot with ordinary allocator, counters/diagnostics off. Variants: set/full, vector/full, set/batch256, vector/batch256, compiled. Twelve cases, two changing queries each: broad width64 with both insertion and binding orders(4); broad width128 forward/forward and reverse/reverse(2); broad width64 admission cancellation in both insertion orders(2); readiness depth64 separate early failure, shared success and shared late clash(3); readiness depth4 separate success(1). One complete session per process and five balanced blocks, for300 measured processes. Shuffle case groups with seed7211; keep the five variants adjacent, rotate their positions across blocks. One warmup per cell,60 processes, excluded. Freeze builds, sources, jobs and toolchain before qualification/warmups/measurements.

Primary endpoint: sum preparation, all setup and execution/observation phases, engine/rules disposal and consumer disposal. Input construction and independent validation remain outside this existing runner endpoint; report that boundary. Source generation and compiler cost are not isolated. Gain/loss screening requires at least10% median paired difference and every one of five paired ratios on the same side of1. Others are unresolved, not equivalent. This pilot is exploratory: consequential candidates/uncertainty require a separately registered confirmation before policy adoption. Use all pairwise contrasts, report scoped results, and preserve adverse cases. Resource failures or unfinished execution cannot count as slow completed samples.
