# E01 v2 — persistent versus copied scalar snapshots

This first storage-control experiment asks how much explicit-OR snapshot copying costs when execution, indexing, unification and observation are held constant. Both modes execute each alternative independently; neither is expected to eliminate B×W common source expansions.

## Implementations and hypotheses

`chr-persistent` is an independently implemented scalar engine. It uses a hash-consed immutable constructor arena, persistent treaps for substitutions/occurrence indexes/history, a shared pending-goal list, committed declaration/occurrence selection and FIFO alternatives. The index key is (predicate ID, occurrence ID); range lookup avoids scanning unrelated predicates. Treap priorities are deterministic hashes; operation counts measure actual tree visits and node creation, without claiming worst-case logarithmic behavior.

Persistent mode retains map/list roots at OR. Copy mode recursively copies every substitution/store/history map node and pending-list node at OR while retaining the same immutable term nodes and values. This is an ablation within one engine, not a tuned candidate versus the copying reference. Both use the independently validated exact answer observer from E14. Their source expansions, source transitions and answers should agree. Persistent mode should avoid snapshot node copies; path-copy updates and all other bookkeeping still count.

The copying reference remains a correctness comparator through E00's independent observations. Differences between its matcher, unifier or canonicalizer and this engine are not attributed to storage sharing. The new arena retains interned nodes for the search lifetime; this is explicitly measured retention, not a reclamation solution. Trailing/replay controls remain later E01 work.

## Cases and validity

Before the comparative batch, both modes must pass the 64 E00 cases, raw multiplicity and prefix/exhaustion checks; separate tests challenge treap snapshots/ranges against BTreeMap, transactional unification rollback, simpagation and ordered propagation tuples. The exact observer compares variable-renamed residuals without importing reference normalization.

Run both modes on the natural carry family with k in {0,1,2,4,8}, W in {0,1,8,64,256}, and unrelated-store size in {0,16,128}: 75 parameter combinations per mode. The actual query posts carry and k pick constraints; the declared rule order resolves picks before carry. Expected carry work is 2^k*W and total applications are 2^k-1 + 2^k*W. This is natural execution under this committed policy, not a fabricated shared continuation snapshot. Run all 64 E00 cases as an additional application/semantic cost batch.

Each run checks actual recognized answers against hand-derived observations, plus raw successes and exhaustion. The maximum carry source-step budget is 1,000,000; E00 cases retain their own limits. A mismatch or exhausted process allowance stops affected measurement and requires investigation. A case taking over 60 seconds is recorded as a timeout, not failure or empty output.

## Measurements and analysis

Record actual source steps/applications, introductions, equations, structural pair visits, dereferences, occurs visits, indexed head candidates, explicit splits, failure, raw/final answers, pending/max frontier, map visits/allocations, snapshot node copies, pending-node allocations, term interning requests/retained nodes and observer work. Instrument a process-local System allocator to record allocation calls/requested bytes, baseline live requested bytes, peak live requested bytes and final live requested bytes. These are allocation payloads, not resident memory or allocator metadata; constructor interning and output retention remain included. Report process overhead separately through the baseline measurement.

This batch uses one release-process execution per case/configuration and one complete replay. Elapsed microseconds are diagnostic only, not a statistically supported speed comparison. Freeze source/registration commit before execution. Check deterministic semantic and operation-count fields on replay; allocation payloads should also be investigated if they vary. Run configurations in recorded case/parameter order. Save all raw TSV rows. Comparative timing with randomized order/repetitions requires a subsequent registration.

Interpret persistent/copy differences only within this engine. Unchanged source work with fewer snapshot allocations establishes storage savings, not common computation reuse. No-OR and W=0 cases expose base overhead. Large unrelated stores test copying sensitivity versus predicate indexing. The first result enables independent mechanism probes; it cannot close E01's trail/replay/reclamation questions or select a production engine.

## Runner reconciliation before the isolated batch

The v1 runner executed cases consecutively in one release process, although the registration specified fresh processes. Its two deterministic count batches are retained as exploratory `E01-storage.tsv` and `E01-storage-replay.tsv`. Their observations do not establish fresh-process timing or allocation baselines.

V2 runs `research/chr-persistent/run_batch.py` after `cargo build --release -p chr-persistent --example batch`. The driver requests the frozen case list, executes exactly one case/configuration per child, enforces a 60-second per-child timeout and preserves every row. Formal v2 results are `E01-storage-isolated.tsv` and its replay. All other parameters and hypotheses are unchanged. Allocator readings bracket engine construction and execution; expected observations and source-case construction exist in the measured baseline, and correctness comparisons execute after the ending reading. Materialized answers retained both by the search and its caller remain included.
