## Exact source and controls

Stable tables contain N distinct ground keys in left(K,P) and right(K,P), each pair
sharing an opaque unknown payload. One rule keeps both partners, consumes
request(K,Round), and posts receipt(K,Round,P,P) plus acknowledgement. An ordinary
run-list producer posts one request and waits for acknowledgement before the next.
Requests alternate first and last keys. After the last acknowledgement, cleanup
consumes one table pair per application, then posts completion. There is no OR.
The consumed request is the last source head, after the two kept heads; no
request-first source reformulation is assumed.

N=16,128; R=1,32. Compare the identical source and queries with Generic execution,
Global/Active selection and Scan/Indexed access:16 cells. Run each twice in fresh
processes for exact non-time reproducibility:32 processes. Python Random seed57057
shuffles the full two-repetition job list. Do not adapt cases based on outcomes.
Generated execution is unnecessary to establish candidate discovery counts; no
runtime ranking between interpreted/generated controls follows.

## Semantic and work endpoints

correct within-key aliases, distinct between-key payloads when both keys appear,
and completion. No table, request or driver residual remains. Exhaustion must be
successful. Source applications are exactly3*R+N+2. Before comparisons, test late
binding and consumed-partner replacement so a future maintenance interpretation
cannot assume all partners remain immutable. Small gates retain source trace/audit
correspondence; screen counts run without trace retention.

Use existing engine metrics for applications, candidate visits, cursor steps,

Any wall measurements are resource diagnostics including validation, not timing
