# Repeated source-driven alias updates: dependency lifecycle opportunity

The corrected local lifecycle sizing charges pair-index construction but performs only one low-yield update. This package varies update count independently from suspended requests to test the index's favorable opportunity before choosing a dependency organization. It uses the existing executable rule and the same seven controls; no runtime mechanism is added.

The source rule consumes `take(pair(X,X),Y), token()` and executes `Y=X`. Post N suspended requests comparing shared unknown U with distinct unknowns, plus M initially ready requests `take(pair(Vj,Vj),U)` with distinct Vj. Each ready source application aliases U to another Vj without resolving the suspended counterparts. All M applications must occur; complete named outputs preserve their correlation, N suspended requests and N residual tokens. Include M=1 as the prior adverse registration control. Query reuse varies variable identities, not the prepared rule.

Hypothesis: Endpoint repeatedly revisits N requests per update; Filtered still receives those notifications but can avoid rematching; Indexed can avoid notification work when the incident class stays resident. Repeated updates may repay pair registration, while memory, query admission, observation and disposal may prevent a total-lifecycle gain. A work-count reduction alone cannot decide the organization.

Use N=32,128; M=1,8,32; prepared reuse=1,4; seven controls (Endpoint, Filtered, local Indexed, generic Scan/Indexed and specialized Scan/Indexed). This gives 12 source/lifetime cells and 84 control cells. Run five isolated counter-free ordinary-allocator timing repetitions (420 processes), two counter-free requested-allocation repetitions (168), and two separate work repetitions (168), totaling 756 processes. Add cancellation after setup and after one service operation at N=128, M=32, reuse=1, seven controls and two allocation repetitions (28 processes). Total 784.

Before timing, check all new sources against independent scalar semantics and require M diagnostic source applications. Keep the same lifecycle phase definitions, borrowed exact answer validation outside intervals, complete observation, answer retention through query disposal and final allocation restoration. Cancellation service units differ across engines and establish restoration, not a speed ranking. Requested bytes are not RSS. Freeze source/binary hashes and commands; run sequentially on one available CPU with 60-second and 1-GiB address-space limits per process and the existing 200000 service-operation bound.

Randomize each repetition block with seed 7205. Report medians/ranges and separate phases; this remains exploratory sizing rather than confirmation. Exactly replay allocations/work, and compare the M=1 cells against prior normalized allocation/work signatures where the source is identical. Diagnose any cutoff, source discrepancy, or consequential control defect before interpreting costs.

This is the third package since the last four-package breadth review. A credible complete advantage can change the dependency organization considered for broader integration. A lack of total benefit despite saved work should be attributed to preparation, retention or observation before selecting further work. Reconsider broader source integration, peak ownership attribution, repeated dynamic reunion and resource-aware lowering at the boundary; do not automatically add another local refinement.
