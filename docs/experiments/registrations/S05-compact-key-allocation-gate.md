# Validate compact-key allocation and ownership before timing

The compact key gate preserves closed subtrees by canonical arena ID and canonicalizes newly ground open terms through arena interning. Owned/compact key expansion and equality checks, independent raw source answers, and matching work signatures pass. This allocation gate checks the intended reduction and possible retention costs before a comparative timing registration.

Use `continuation_cost` in a counter-free meter build, with ten modes: direct/exact/alpha/live/scan/sealed/dependencies/compact-exact/compact-alpha/compact-live. Sources are exact/rename/history/history-early/distinct, depth0/64, resources absent/present, two changed queries, forward starting order: 20 source configurations and 200 engine cells. Changed queries use depth n/n+1 and alternating order. Run two allocation repetitions, requiring exact payload replay for all 200 cells. Cancellation uses history-early/depth16/two queries/resources/forward, one tick, all ten modes: ten additional meter processes. Total 410 allocation processes plus meter self-check. No ordinary timing comparison or speed classification is part of this gate.

Freeze source, binary hashes, compiler and driver before runs. Use first available CPU, 60-second wall/CPU and 1 GiB address-space limits, plus the existing two-million-step source/scalar bounds. Complete independent raw answers are validated outside phase intervals. Query and prepared requested-live bytes must return to their baselines after disposal; retain and investigate every failure or cutoff.

Record requested allocation by phase and peak requested growth. Include preparation, setup, execution/complete observation and engine/answer/prepared disposal; source/input construction remains separate. Meter elapsed times are not evidence of speed, requested bytes are not RSS, and native compilation is excluded. Compare each compact mode with its owned counterpart, retaining all adverse cases. Gate findings do not choose an architecture or substitute for total timing/lifetime comparison.

The compact and owned alternatives share traversal/canonicalization code and differ in term representation and machine ownership. Interning resolved ground terms can create new arena nodes, so do not claim that all allocation differences come solely from skipped copying. Existing mode layout is compiled into the same binary for these paired allocation comparisons. After the gate, conduct the scheduled breadth review before more refinement or paired timings. Call-level reuse, broader relevance and sustained lifetime remain required.
