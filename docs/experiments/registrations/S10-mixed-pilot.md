# Complete-query mixed-source cost pilot

Test the qualified Rust execution organizations and combined native host on the same complete-query batches. H1: a native graph path may or may not repay its frontend, preparation and publication costs against the strongest applicable Rust organization. H2: service-only ordering can differ from complete process ordering. H3: favorable regimes may differ by source; no workload weights or universal winner are inferred.

Select every nonempty complete subset of the frozen s10-native-common-source/groups.json and s10-native-substantive/groups.json: twenty common groups and four substantive groups,24 batches total. Exclude ongoing-only common groups10/11 from completion comparisons, retaining them as explicit progress/lifetime obligations. Preserve source order within batches. Use all13 Rust modes0–12 and the combined native host as candidates. Unsupported programs remain capability exclusions, never failed timing samples or silent fallbacks. Freeze selected full sources and hashes in selection.json before execution.

Use the previously qualified rust-primary and native-primary binaries from target/s10-publication-clock, checking their archived hashes. The current host emitter lifetime correction is included; all its emitted programs are already checked identical. Native invocation uses the explicit primary host runner. Source budgets are200000 per Rust query and1048576 native service calls; these are protective limits, not equal work. Only independently verified complete outcomes enter timing comparisons. Every run validates full decoded answers, aliases, multiplicity and completion outside its measured interval.

First run one eligibility/correctness process for each of336 candidate/batch pairs on CPU0. These are excluded from cost analysis. Keep explicit unsupported rows. Freeze eligible pairs before timings. Run one excluded warmup per eligible pair on each CPU0/1, then five measured repetitions per pair per CPU. Use randomized order with seed20260917 for warmups and measured jobs separately. All primary runs use ordinary allocation and disabled diagnostic engine/serialization counters; operational identity and service budgets remain. No allocation/tracing diagnostic runs enter this timing set.

Primary endpoint: parent-observed elapsed around invocation through captured batch output and process exit. It includes process startup/imports, source input, preparation, changed-query execution, owned observation, publication and disposal. Record named internal lifecycle phases separately; native phases are nested in host process time and must not be added twice. Internal first-answer times are not cross-path external latency. Compilation of runtime binaries or user programs is not measured. This is a comparison of concrete complete batch paths within that scope, not complete architectural lifecycle superiority.

Use30 wall seconds per process,20 CPU seconds and96GiB address-space allowance for the established native mappings (same outer allowance for candidates, not a claim of comparable residency). Bound the whole invocation at1200 wall seconds and600 cumulative child CPU seconds. Stop and diagnose any bound, nonzero exit, unexpected output or incompletion; do not label a cutoff an architectural loss. The corpus has independently qualified outcomes, but the new batching must pass its entry check.

Interpretation is a bounded exploratory screen: a practical gain requires at least10% lower median and nonoverlapping five-sample ranges on both CPUs; reverse conditions give a loss, otherwise unresolved. Report per-batch ratios and each CPU's spread. The fastest admitted Rust median may be displayed as an exploratory oracle control, explicitly not a deployable source-selection policy. No significance or unseen-source generalization follows from this small pilot. Investigate consequential overhead or a reversal; do not tune to every sample. After this pilot and necessary attribution, revisit T073 and the distinct-mechanism sequence.
