# Mixed-phase conditional/explicit lifecycle comparison

Prospective T042 comparison, selected by the [publication-flow gate](../results/R06-publication-flow-gate.md). Question: do conditional savings survive the transition from opaque common work to constructor discrimination and subsequent identical common computation? Existing homogeneous regimes and separate-session control measurements do not answer this interaction. The comparison needs fixtures and independent observations, not a new backend or an assumed hybrid policy.

The source starts four independent binary choices, then an opaque pre-countdown carrying their tuple and a shared unknown. Its base posts a gate with16 constructor-specific rules. Each gate posts the same post-countdown computation plus a witness of its tuple with a repeated unknown. The post base emits a done residual sharing that unknown. Full answers are exactly16 tuple keys, each with the prescribed witness/done alias relationship and no other residuals or outputs. Work depths enter through queries; all queries reuse one prepared ruleset. Independent integer tuple keys/full-structure checks must pass before timing. Source-application counts are explanatory predictions, not semantic acceptance criteria.

H1: pre-discrimination applications remain shared in conditional execution; separately created post occurrences prevent the same saving afterward. Predicted aggregate applications are `pre + 16*post + 34` for conditional and `1 + 16*(pre+post+3)` for specialized explicit; the shared initial start application must not be charged once per output. H2: savings depend on work placement even when total countdown depth is fixed. H3: maintenance and observation/preparation overhead may dominate small or post-heavy cases. A differing valid count requires explanation rather than forcing a trace; an answer discrepancy invalidates cost evidence.

Exact depth pairs: (0,0), (0,16), (8,8), (16,0), (0,64), (32,32), (64,0). These include no-work, early/late discrimination and balanced placement controls. Backends are current conditional and inferred-specialized explicit Global/Indexed. Query counts1 and4; query i uses (pre+i%2, post+i%2). Thus28 cells, one warmup, five primary repetitions, one allocation run and one work run each:224 fresh processes. Random(42043) shuffles within modes. There is no aggregate weighted winner, and stage proportions are experimental inputs rather than an assumed application distribution.

Measure source cloning/preparation, query cloning/setup, combined execution and full observation, first answer, engine disposal, output disposal and final prepared disposal. Retain each query's16 complete answers through its execution; validate outside measured backend intervals with an allocation-free closed-form checker, then measure output disposal. Later intervals are validation-warmed. Keep original syntax and fixed measurement records outside the live-heap baseline until the final reading. Attribute requested live/peak/traffic separately from timing; requested heap is not RSS. This boundary is specific to this paired comparison and cannot be silently combined with older retained-batch timings.

Primary release uses ordinary allocator and `--no-default-features --features experiment`; allocation uses `--no-default-features --features alloc-meter`; work uses `--features experiment`. Separate target directories. Prepared rules are truly reused; source/kernel counters must be disabled in primary. Full-branch work aggregation must count retired split prefixes once. Capture compiler/host/source/binary hashes, commands and all outcomes; meter self-check and final source/binary freeze required.

Run serially on one inherited CPU. Caps:20million service ticks per query,30seconds and1GiB address space per process,30minutes execution budget after builds. Preserve cutoffs, errors, incomplete/missing cells and outliers; do not resize based on outcomes. Full raw tuple coverage, aliases, exact count and exhaustion are required. Every allocation process must restore its baseline after all measured owners are disposed.

Report medians/ranges for complete lifecycle/query and phases, first answer, allocation and source counts for every cell; partial endpoints are not complete timing competitors. Overlapping timing ranges remain inconclusive. Compare fixed-total work placements to explain the transition; no claim that identical post work is necessarily impossible to combine in another organization. If a boundary is characterized, assess its architecture implications rather than automatically implementing reunion or mode switching.

This finite constructed pipeline also permits analytical simplifications under stronger static correspondence/termination knowledge. The pilot does not establish that CHR execution is necessary or beat such a lowering. Its decision is the applicability of these current execution organizations when this mixed work is performed; broader static eligibility, native compilation, parallel granularity and lifetime ownership remain open.
