# Size complete lifetime costs with selective reclamation

The [reclamation gate](../results/S08-metadata-reclamation-gate.md) validates removal of incompatible result entries and claims without changing tested graph service. This prospective pilot asks whether reduced retention can repay scanning and shrinking. It supplies exploratory costs, not confirmatory speed classifications.

Use stream families repeated/distinct/aliases; depth16/64; work0/4; payload0/8; resource absent/present; and immediate-release/window-four/retain-all consumers: 144 configurations. Each preparation serves two changed queries at depth n/n+1, forward then reversed input order. Successful terminal branches define this cost matrix; failing streams and contested-resource policy differences retain separate semantic evidence and future cost obligations.

Eleven controls: direct continuation execution; compact-live continuation reuse; Scan; specialized Scan; dependency graph retaining all metadata, reclaiming after each answer, or reclaiming after every16th answer; the same three template-graph policies; and checked lazy exact-source generation. Reclamation is part of execution/observation, including scans and vector shrinking. Do not perform an uncharged final collection when the stream ends between maintenance boundaries. All controls use the same build and source; no graph collection policy is silently made the default.

Native compilation and RSS are outside this pilot; allocation-meter elapsed times are not speed evidence.

Interpret differences pointwise with their source and consumer contract. A single ordinary sample cannot establish a practical gain/loss. Check whether reclamation changes retained memory before exhaustion, whether scanning becomes consequential, and whether retaining useful cached results is cheaper. An exact-source advantage does not prove a general compiler can derive that generator. A cutoff calls for investigation, not a performance loss label.
