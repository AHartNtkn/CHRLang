# First locate retained owners during progressive answer delivery

This allocation-only source/ownership probe follows the S05 next-investigation review. It tests whether memory remains with a still-live engine after consumers release answers. It does not compare speed, claim sustainable asymptotics, or select a reclamation policy.

The source chooses between emitting one answer and continuing a finite stream. Repeated ground values, distinct growing tags and unknown aliases vary answer relationships. A carried payload and independent wait countdown separate output size from work between answers. Optional completion consumes a token only after the output constructor is available. The terminal branch can explicitly fail. No source scheduling or observation contract is changed.

First validate scalar semantics against an analytical formula over three families, resource/failing-tail flags, depth0/1/4/16, work0/3, payload0/4 and both query orders: 384 configurations. Compare seven controls (direct, compact-live, Scan, specialized Scan, graph dependencies, graph templates, checked lazy exact-source generator), 2688 mode/source runs. Separately validate immediate-release, window-four and retain-all consumers, including cancellation after four answers and complete raw multiplicity. All preparation is reusable across changed queries.

Then freeze source, compiler, binary and this registration for a requested-allocation probe using release, no default features and alloc-meter; reject diagnostic counters. Run three families, depth16/64, resource absent/present, work4, payload8, successful terminal, all three consumers and seven controls: 252 cells, twice for 504 processes. Each process runs depth n then n+1, with reversed input order in the second query, over reused preparation. Repeat cancellation after four answers in the first query on aliases/depth64/resources, all three consumers and seven controls, twice: 42 processes. Total546 registered processes plus meter self-check. Require exact allocation replay, full query/prepared live restoration and no hidden output retention in the harness.

Record live requested bytes at setup, answer counts1/4/16/64 where reached, final delivery, consumer release with the engine still alive, and engine/prepared disposal. Use a preallocated consumer-slot buffer and checkpoint buffer outside the measured owner baseline, equal across consumer policies for each source size. This excludes fixed harness slots, not the allocations owned by answers. Validate the full source in an unmeasured replay before the allocation probe; do not hold those expected/actual answers during the measured run. Preserve observed counts and termination/cancellation status in the receipt.

Use a 60-second wall/CPU bound, 1GiB address-space limit, first available CPU affinity and two-million-step scalar/service bound. Preserve every failure and cutoff. There are no timing classifications or outlier exclusions. Requested allocation is not RSS. Growth across two finite lengths is evidence to investigate an owner, not a proof of asymptotic growth. A retained owner must be traced to its actual future obligations before proposing reclamation or declaring the retention necessary.

Reconsider broader call-level reuse and integrated execution after this source/ownership gate and the first lifetime cost package. Sustained ordinary timing, larger regimes, failing-stream costs, compact output contracts and publication policies remain required.
