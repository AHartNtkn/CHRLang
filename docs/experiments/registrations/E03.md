# E03 v1 — finite supports and common source expansion

This first conditional-store probe tests pointwise behavior and physical common expansion with all bookkeeping exposed. It is the complete-scan, extensional-support part of the broader T013 comparison, not completion of T013's incremental/BDD/generated-trace obligations.

## Concrete machine and comparison

One store maps occurrence identities to immutable constraint data and live support sets. Variable bindings and propagation tokens have explicit finite supports. Variable/occurrence birth supports remain separate from live membership. Splitting a ticket pulls every existing support back to its two fresh children; inactive decisions never enumerate extra leaves. The frontier has one pending-work queue per live ticket. Failure/completion retires that ticket from service; this first implementation retains historical support records and does not claim reclamation.

Unification processes one projected equation transactionally, then publishes its binding edges only on that ticket. This is an exact finite-support baseline, not an optimized symbolic occurs algorithm. Matching scans current physical occurrences and checks supported membership without binding store variables. A catchall head preserves a raw logical handle; constructor demands dereference it in the ticket's context. Guards retain the reference equality-entailment contract. Exact answer comparison uses the independent E14 observer, never the reference normalizer.

Singleton mode performs one source operation on the oldest ticket. Ready-group mode snapshots up to 256 ready tickets and groups only Apply operations with identical rule, occurrence tuple and raw matching witnesses, or Introduce operations with the same pending-work identity. It instantiates one body or inserts one occurrence for the group. Conjunction/OR child work identities are created with that body and remain shared when queues consume them. Other operations remain singleton. Birth support for fresh body variables is exactly the group support. Different occurrences do not acquire the same fresh variables merely because printed arguments coincide.

Both modes use the same conditional equality, store, matcher and observer. Compare them to isolate grouping within this representation. E01's scalar control supplies a source-work baseline, but its indexed immutable representation differs, so cross-engine timing is not an isolated grouping comparison.

## Fidelity evidence required before measurement

Both modes must match the 64 E00 expected observations, raw successful alternatives, and completion/prefix status. Check live projections after every tested quantum: binding targets exist in that ticket, outgoing bindings are disjoint, projected equality is acyclic, occurrences lie inside birth support and tokens refer to born occurrences. On semantic cases, capture every unserved projection before/after a quantum and require exact equality. Include the later-equal-branch propagation example, where one branch acquires a token before the other becomes enabled.

These are endpoint and invariant/frame checks. They do not replace the still-required coupled scalar transition comparison or generated bounded traces. A checkpoint API exposes raw runtime projections to the experiment, not to source rules.

## Registered cost matrix

Run the 64 E00 cases, plus the natural carry grid k={0,1,2,4,8}, W={0,1,8,64,256}, noise={0,16,128}, in both modes. Expected complete answer sets and raw counts are unchanged from E00/E01. Carry cases receive 1,000,000 conditional quanta; E00 cases retain their own bounds. A quantum may serve multiple projections, so a quantum count is not a scalar step count.

Add immediate-discrimination cases k={1,2,4}, W={1,8,64}, noise={0,16}. These replace the opaque carry rule by 2^k constructor-headed rules, one per concrete tag, each performing the same countdown with its tag. This preserves the registered outputs but forces a distinct source rule per tag at every step. Report the larger ruleset as part of the adverse source family, not an unexplained engine penalty.

Hypotheses: on the synchronized natural opaque chain, Ready mode performs k+W physical expansions while representing 2^k-1 + 2^k*W applications; Singleton performs the latter number of expansions. Immediate discrimination should prevent common carry expansion, although common choice preparation can still be grouped. Ordinary rule competition remains committed, not searched.

Record actual quanta, projected steps/applications, physical expansions/introductions, support membership reads and changed memberships, occurrence/binding scans, matching candidates, term visits/copies, equation pairs, occurs visits, previews, queue scans/reference copies, work nodes, frontier size, raw/final answers and observer operations. Report retained occurrence/binding/history/birth counts and support memberships. Support calls have operand-size-dependent cost; their counts are not constant-time or total-runtime claims.

Use the same process-local allocation meter as E01's example (instrumentation only) to record requested payload and baseline/peak/final live bytes. This does not expose either scalar engine's execution algorithms. Materialized outputs and retained historical supports remain charged. Constructor data in this baseline is owned syntax data rather than E01's interned arena; record that asymmetry.

Freeze the source and registration before runs. Execute each case/mode in a fresh release process with a 60-second timeout, once plus a full replay; compare non-time fields. Elapsed time is diagnostic. Record timeouts as inconclusive rows and keep independent cases moving. The total matrix has 157 cases and 314 case/mode runs. No timing winner or architecture adoption follows from this batch.

## E03 v2 — eliminate repeated subtree copies during observation

The v1 batch exposed very large term-copy counts even at W=0. Inspection found that `resolved` deep-copies a term through `deref`, then recursively repeats that copy for each child. On a unary ground term of depth n this performs quadratic temporary copying during observation. This is an implementation defect in the observer adapter, not a required support-representation cost.

Before v2 comparative runs, add a depth-128 ground observation check requiring exactly one copied node per returned node, implement borrowed contextual dereferencing for resolution, and keep the unification/matching and grouping policies unchanged. Run the complete registered matrix and replay again into distinct v2 files. Expect unchanged answers and all source/scheduling/support counters, with fewer term copies and allocations where structured answers occur. The v1 files remain valid observations of v1, but their allocation overhead cannot be attributed solely to finite supports or grouping. This intervention isolates observation copying; owned runtime terms and other services remain separate follow-ups.
