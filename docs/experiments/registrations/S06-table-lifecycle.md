# S06 finite table compilation: prospective lifecycle pilot

Compare direct source-derived joins with generic dedicated execution under Global policy, using Scan and Indexed access. The decision is whether eliminating the CHR execution loop repays source certification and relation/index construction on the admitted finite fragment. This does not rank generated native code, R04's differently represented finite solver or unrestricted CHR.

Six families: sparse diagonal tables with 32 values; dense binary tables with four values; four-value diagonal tables with each left row duplicated; two disconnected four-value diagonal tables; a four-value diagonal relation queried with an impossible first value; and a one-value tiny relation. The ordinary request calls ab(X,Y),bc(Y,Z); the disconnected request calls ab(X,Y),bc(L,Z) with fresh local L. Every ruleset also has pin(X) with its sole row k0. Table rows are actual source OR alternatives. The raw answer bag retains duplicate row derivations and an opaque unknown carried in a passive residual.

Query variants are free arguments, an added pin(X), repeated X/Z, and an added pin(Y). Contradictory-family requests instead fix their first argument to outside-domain k99. Sessions run either one free query or 16 queries cycling the four variants. Both include new measured preparation and complete prepared disposal; therefore the comparison includes one-use versus reused preparation. Four unmeasured warmup queries precede each session.

Validate runner answers against a separately constructed row-product oracle outside measured intervals; also validate that oracle against independent scalar source execution before freezing. Charge preparation, query setup, joint execution/observation, engine disposal, answer disposal and prepared disposal. Input AST construction, input cloning and validation are outside timing; required preparation cloning is inside. First-answer latency is recorded separately, overlaps execution and is never summed twice. A no-answer query has null first latency and must exhaust truthfully. Native compilation/process startup are excluded, so there is no complete cold-architecture claim.

There are 36 cells (six families × three engines × two session lifetimes), five primary repetitions and two allocation repetitions: 252 isolated processes. Randomize within repetition with seed 20260910. Use counter-free release builds, ordinary allocator for primary timing, separate requested-allocation diagnostics, the lowest permitted CPU and recorded source/binary/toolchain hashes. Bound each process at 60 seconds and 1 GiB, each query at 2,000,000 advances and 10,000 answers. These bounds are operational, not evidence against a cutoff design. Stop and investigate any failure or cutoff.

Analyze per-cell lifecycle medians/ranges, paired within-repetition ratios, phase costs and one-use versus reused preparation. The pilot's practical signal is a ≥20% paired median difference with all five ratios on the same side of one; uncertainty crossing a consequential decision requires investigation. Verify exact allocation diagnostic replay across both repetitions. Requested allocation is not RSS; distinguish traffic from live baselines. Investigate consequential losses or crossovers before declaring a bounded disposition. Broader lowering, relation representations and language-property investigations remain open regardless of this pilot.
