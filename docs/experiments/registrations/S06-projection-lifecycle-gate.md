# Projection ordering and observation qualification

Register before implementation or comparative runs. This package qualifies input-derived ordering and owned expanded observations; it makes no timing or heap superiority claim. T076 remains active. The previous projection entry is package one after the descriptor breadth review; this qualification is package two. Adaptive ownership/costs remain the strongest ready alternative. Projection gets this package because its correct hidden-work elimination cannot enter a credible cost comparison until ordering and output obligations are explicit.

## Hypotheses and controls

A greedy order using only factor scopes and distinct domain sizes may avoid the connected star's large intermediate factor. At each step estimate the Cartesian size of the union of scopes containing each hidden coordinate, choose the smallest, break ties by union width then coordinate ID, and replace those scopes with their union minus that coordinate. Empty domains give zero estimated work; saturating u128 scores are estimates, never semantic counts. Do not inspect future answers or workload labels. Compare with ascending and descending fixed orders and independent enumeration. This is a candidate heuristic, not an optimal-order claim; charge its entire construction in subsequent cost runs.

An owned iterator can expand counted visible tuples without retaining all repeated outputs. It must preserve the complete answer multiset, remain usable after preparation is disposed, and release its pending outputs on cancellation by ordinary drop. It does not reconstruct source derivation order or hidden witness provenance. Include an explicit order counterexample: two independent Boolean choices with the first hidden produce visible sequence 0,1,0,1 in direct lexicographic source-choice traversal, whereas grouped expansion produces 0,0,1,1. This rules out treating grouped expansion as the same ordered endpoint. A later source mapping must prove that the chosen observation contract permits grouping, or preserve the required order separately.

## Exact qualification matrix

Use 256 deterministic generated finite problems with 3–6 coordinates, values 0–2, duplicate domain choices, occasional empty domains and 0–3 unary/binary/ternary membership filters. Seed 0x9e3779b9; LCG multiply 6364136223846793005, add 1, take upper 32 bits. For each problem use eight visible masks, both set/count semantics, and greedy/ascending/descending hidden orders. Independently enumerate original domain-choice tuples and test membership without projection; compare complete weighted maps. For the greedy order also compare every singleton visible restriction to values 0–2, and fully expanded multisets. Include reversed visible-coordinate order in a dedicated witness.

Dedicated controls: the eight-coordinate connected star from the entry; 24 independent Boolean coordinates with one visible coordinate; ten visible Boolean coordinates with dense required output; changing restrictions against one prepared projection; empty and zero-coordinate problems; duplicate/invalid coordinate and relation inputs; counts exceeding a registered output bound; and cancellation after a small prefix of 2^24 represented outputs. Use source snapshots from the previous qualified entry to preserve its frozen evidence when production code changes.

## Endpoints, bounds and interpretation

Expansion first obtains the complete weighted map, then checks its total against a caller-supplied u128 output limit before returning an iterator of independently owned tuples. Count arithmetic is checked; exhaustion, output-bound error and arithmetic overflow remain distinct. Expansion is grouped in visible-tuple order. First expanded output therefore includes prior weighted materialization; it is not an incremental first-answer endpoint. Retain this cost boundary in any subsequent comparison.

Compile default and metrics-off tests separately. Freeze source and binary hashes before direct execution. Run the new lifecycle suite plus existing projection and finite-path suites once per build: six correctness processes, each 60 seconds wall/CPU and 1 GiB virtual address space. Correctness repetitions are deterministic, not statistical measurements. Run Clippy for the affected tests in both configurations. No comparative timing or allocation matrix is authorized by this registration; a prospective lifecycle registration follows credible endpoints and ownership measurement. Record actual work counts as diagnostics only.

Passing establishes this finite map/expanded-multiset endpoint and ordering policy. It does not establish CHR source-order equivalence, general privacy inference, arbitrary structural paths, effectful hidden work, measured retention savings or a preferred architecture. A consequential failure receives repair or a scoped limitation before proceeding. Reconsider adaptive costs and other required directions at this gate; full breadth review by package four.
