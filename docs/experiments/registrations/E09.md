# E09 — scheduling and finite service

E06's completed net service makes this investigation ready independently of its
remaining native/compiler refinements. Those questions stay queued and open.
Compare per-alternative FIFO, sealed symbolic rounds and asynchronous sealed jobs
on the same operations; preserve source identities independently of shared work.

## First prerequisite gate: whole-request yields

The E06 harness reduces nets in finite quanta but builds inputs and reads complete
results atomically. Expose a sealed UnificationJob whose immutable inputs are
already in the encoded backend data representation and whose rule system is
prepared once and shared read-only. Request admission allocates only fixed-size
control state. Do not hide rule compilation in each admission.

Yield on each input data node or header operation, each actual net interaction,
each stored-node validity check, and each output visit/assembly operation. Delay
reduction until the private graph is fully wired. Delay publication until both
complete outputs are materialized and no active/stuck controller remains. Keep
original-table preservation and failure privacy from E06.

The fixed data signature and rule interfaces bound explicit graph work per action.
Python allocation, dictionary resizing and garbage collection do not have a
hard wall-time bound. This gate establishes finite resumable service, not real-time
scheduling. Input/source compilation, support management, source matching and
final answer deduplication remain separate operations requiring their own accounting.

Validate the 96 existing unification workloads at quanta 1,8,64, up to 250,000
service actions each. Require complete independent expected observations and
exact per-phase work agreement across quanta and replay; record quantum-dependent
resume counts separately. Test rejection of observation throughout partial build
and readback. Interleave a small identity with a large request during both build
and read phases and require the small request to finish while the large request
remains in that phase. These are service-isolation tests, not a complete source
scheduler comparison or a general fairness proof.

## Scheduler questions retained

Implement the three policies and grouping/quantum factors after this gate. Include
divergent source siblings, large equalities and tuple scans, source wake-ups,
nested explicit choices inside shared work, partial supported completion and
duplicate-heavy observation. Charge support/selector work and observer costs;
completed supports may publish without awaiting unrelated work. A sealed round
barrier can delay the next source step even when individual services yield.

The liveness claim must state immutable finite inputs, finite operation completion,
finite predecessors, preserved queue age under splitting, a draining observer and
available storage. Different queue ordering alone cannot repair an atomic
unbounded backend normalization. Do not generalize one service's results to other
matching/observation implementations; E15 owns the required second-service check.

## Source adapter gate (before policy comparisons)

Use an independently implemented resumable direct-tree source adapter with the
same fixed committed selector as the existing controls. It is an explicit direct
service factor, not net integration. Check every continued/forked state against
the independent E11 tree interpreter, including occurrence IDs, propagation
history, pending goals, fresh variables and substitutions. Check terminal answers
against both the hand expectations and Rust reference for all 64 E00 cases.
Use source-step budgets and answer limits from those fixtures; run service quanta
1, 8 and 64 with a 2,000,000-action cap per source step. Record action counts,
source transitions, raw answers, exhaustion and exact replay. No timing superiority
claim comes from this correctness gate. An action cap failure remains a failed
validation requiring investigation, not a semantic answer.

Queries are initialized before source-step measurement; initialization and host
collection allocation must be accounted for separately in comparative runs.
Instrumented traversal/copy actions are resumable, but Python collection freezing,
hashing and permutation advancement do not have a constant wall-time guarantee.
The full residual alpha-equivalence checker is an independent validation oracle;
it is not yet the resumable final observer for policy runs.

## Exact observer service gate

Before scheduler runs, independently implement yielding joint alpha equivalence
of selected outputs and the full residual multiset. A bijection must be shared
across both; branch-local mappings must roll back when residual permutation
matching fails. No entailment/subsumption inference is permitted.

Cross-check every ordered pair of 64 generated observations (four output patterns
`[]`, `[X]`, `[Y]`, `[X,Y]`, crossed with all ordered pairs from `p(X)`, `p(Y)`,
`q(X)`, `q(Y)`) against the independent recursive checker. Also compare each E00
expected/reference answer pair within its case. Run at quanta 1,8,64, with a
2,000,000-action cap per comparison, and require exact decisions/action replay.
This finite symmetry/multiplicity gate supplements explicit alias/backtracking
and incomplete-publication tests; it is not a complexity bound. Observer input
ownership and dedup queue scheduling still require integration checks.

## First integrated policy factor: exact-state supports

Implement singleton FIFO, sealed rounds and asynchronous sealed batches over the
validated direct source/observer services. In this first factor, sharing requires
exact complete state equality (including fresh counters, occurrence IDs, pending
work and history). A shared step therefore has one result throughout its support;
this factor cannot establish contextual selector subdivision or partial completion
inside a heterogeneous family. Keep that broader question open.

Represent lineage using persistent binary-arm and disjoint-union expressions,
with multiplicity cached, rather than enumerating grouped leaves. Explicit OR
appends a bit to each represented path. Seal at most eight ready entries per
admission batch; grouping compares only that finite snapshot and never absorbs
new arrivals into running jobs. Compare state equality resumably and charge its
traversals. Singleton FIFO disables grouping and admits one entry per batch.
Grouped round/async also have a grouping-off control. Round successors wait for
all current evaluator/commit jobs; completed answers enter observation immediately.
Async successors enter at the tail without that barrier. A separate serial exact
observer receives alternate service opportunities while busy, preventing concurrent
acceptance races; later candidates do not enlarge its comparison set. Count raw
multiplicity separately from unique output publication.

First establish conformance on all exhausted E00 cases, at quanta 1,8,64, with
5,000,000 total instrumented actions per case. Prefix cases need different
scheduler-sensitive limits: independently verify every returned answer and retain
finite-sibling progress probes rather than require the reference's exact prefix
order or source-step count. Record any bound failures without calling them answers.
Test support expansion against explicit paths, nested OR multiplicity, private
state updates, grouping on/off equality and deterministic replay. Comparative
latency/cost workloads and resource bounds will be registered after this semantic
gate; conformance data do not establish performance superiority.

## Controlled policy work/latency matrix

Freeze four workload families before comparative execution:

- `lag`, constructor depth 4,16,64: one OR arm performs a large identity equation
  then returns `b`; its sibling takes a small additional source step then returns
  `a`. Hypothesis: a round barrier delays `a` after the small operation completes;
  async can advance it while the large equation remains in service.
- `duplicates`, choice depth 2,4,6: identical true/true ORs precede a returned `a`.
  Hypothesis: exact-state supports avoid repeated source work while preserving
  2^depth raw alternatives and one exact unique observation.
- `opaque`, constructor depth 4,16,64: choose output `a`/`b`, then perform four
  independent large identity equations. Counter-hypothesis: complete-state keys
  cannot share these equal operations because selected output bindings differ.
  No result here may be generalized to conditional-operation sharing.
- `recursive`, constructor depth 4,16,64: a recursive arm repeatedly performs a
  finite identity equation and reposts its constraint; the sibling returns `a`.
  Stop after that one unique answer, verify ongoing live search and its exact
  observation. This is a finite-prefix liveness probe, not an exhaustion claim.

Run singleton FIFO, round grouping off/on, async grouping off/on, each at quanta
1,8,64: 180 configurations, plus exact deterministic replay. Use a 5,000,000-action
cap. Require independently constructed expected observations, raw multiplicity for
exhausted cases and all finite endpoints, with prefix mode explicitly marked.
Measure source actions/jobs, represented source transitions, grouping actions,
observer actions, admission/commit actions, first and per-answer publication action
indices and queue peaks. All bookkeeping categories contribute to latency counts.
Report them as instrumented work/latency, not time, bytes, a universal fairness
proof or native-engine performance. Query construction, wall-time/byte costs,
large tuple selection and heterogeneous-support subdivision remain separately
required investigations; this matrix is a controlled mechanism comparison.

## Mixed tuple selection, binding and batching

Freeze four source workloads at noise/store sizes 4,8,12:

- `scan-lag`: a large branch retains N ground constraints and performs an
  unsuccessful three-head tuple scan. A sibling reaches an enabled small rule at
  the same source depth and needs its resulting equation before answering. Check
  partial answer publication separately from exhaustion and total work.
- `binding`: an initially nonground head cannot match `p(a)` until an explicit
  branch-local equation binds it. One child consumes that constraint; the other
  retains `p(b)`. Both retain the unrelated noise store.
- `guard-binding`: a pure equality guard becomes enabled only in the `a` child;
  the `b` child returns a nonground output with its unsatisfied mark constraint.
  Preserve joint output/residual aliases without assigning guard effects.
- `history`: two explicit identical binding alternatives enable one propagation
  instance each. Preserve two raw lineages, one unique answer and exactly one
  propagated residual per lineage; shared history cannot leak between alternatives.

Every family includes the unsuccessful three-head rule; pending equations follow
normal source priority. This adapter rescans frozen state rather than using a
wakeup index. The binding cases test semantic re-enablement and fairness under
rescan work, not efficient incremental wakeup claims.

Check hand-derived complete observations/raw multiplicities against the independent
E11 tree control before policy runs (30,000 source-step cap). Compare FIFO at its
fixed singleton admission, round/async grouping off and identity grouping on, at
batch sizes 1 and 8 and quanta 1,8,64: 324 configurations and exact replay. Require
exhaustion and the complete joint-alpha/full-residual answer sets, under the common

## Predicate-filtered source selection

Add an explicit selector factor: full ordered tuple scan versus a yielding
predicate/arity filter rebuilt on each frozen source step. For each head, scan
stored occurrences in their existing order, dereferencing root aliases without
binding, and retain compatible roots. Enumerate the Cartesian product in head
order, rejecting repeated occurrence IDs. This yields exactly the subsequence of
original ordered tuples that can match; rule order and first enabled application
remain fixed. Charge pool construction, root dereferencing and duplicate rejection.
This is a rebuilding filter, not a maintained index or indexed-wakeup claim.

Validate every source transition against the independent tree control for all 64
E00 cases at quanta 1,8,64 (192 configurations), including registered nonexhausted
prefixes. Add explicit root-alias, unknown-root and ordered multihead tests. Keep
the 2,000,000-action per-step cap. Recheck the preceding mixed matrix with the
filtered service (324 configurations), plus two matching-predicate countercontrols:
three q heads with an always-false pure guard, and a three-edge cyclic join over
a finite acyclic path. Use sizes 4,8,12; both selectors; FIFO and ungrouped
round/async with batch 8; quanta 1,8,64 (108 configurations). The former exposes
product/duplicate overhead when filtering cannot prune; the latter leaves actual
join work after predicate pruning. Require independent expected answers, raw
multiplicity and exact replay. Use the same 5,000,000-action run cap. No timing or
byte claim follows from this action comparison.

## Distinct-prefix matching

Add a `prefix` selector using the same predicate pools, with a resumable depth-first
iterator in original head/occurrence order. Extend only distinct occurrences;
resolve and nonbinding-match each head before exploring its suffix. Each child
owns copied pattern bindings and used-occurrence state; failed matches cannot
contaminate siblings. Return complete bindings to the ordinary history/guard/body
logic without rematching heads. Keep guards at the full-tuple boundary in this
ablation; early guard placement is a separate semantic/cost question.

Require explicit tests for failed-prefix rollback, repeated pattern variables,
first enabled tuple order and history exclusion. Check 192 E00 source/quantum
configurations, 324 existing mixed configurations and 54 matching-predicate
configurations (prefix, three ungrouped policies, three quanta), plus exact replay.
Use the existing step/run caps and independent controls. Reproduce the preceding
624-row selector matrix to verify that the control services retain their observations
and action counts. Compare prefix/copy/discovery work, not only complete tuples.
A guard-rejected tuple with individually compatible heads may still require full
extension; preserve this adverse workload rather than moving the guard early here.
