# Physical residency and Python host allocation scope

Measure Linux process residency in a diagnostic native build that uses ordinary allocation, independently of the direct-call allocation wrapper. Read current RSS/anonymous/private-dirty from /proc/self/smaps_rollup and virtual size from /proc/self/status at entry, runtime initialization, preparation, service end, query reset, preparation disposal and consumer disposal. These are checkpoint samples, not a continuous peak. Calibrate with a16MiB anonymous mapping: untouched reservation, explicitly touched pages and unmapping. Expect touching to add at least15MiB RSS and unmapping to release at least15MiB in this isolated probe; do not assert zero final process RSS.

Replay the same26 sessions/479 queries twice with original budgets and keep flags. Exact wire bytes and native work signatures must agree with qualified evidence; residency need not be identical between processes. Preserve the native primary binary. Use30-second/20-CPU-second/96GiB process limits. Do not interpret diagnostic times as primary timing.

Separately run the qualified primary host with Python tracemalloc enabled only after imports. Capture traced current/peak bytes and tracer metadata at existing phase boundaries, plus host RSS from smaps_rollup. State that this includes diagnostic checkpoint bookkeeping, excludes pre-trace imports and may omit C/libc allocations. Record retained traced allocations by traceback after the host returns, so live diagnostic objects and interpreter/library retention are distinguishable from task owners. Preserve the externally owned-wire endpoint and temporary cleanup on the26 sessions, with two diagnostic repeats. No subtraction of uncertain baselines and no assertion that all Python process memory must become zero.

These measurements qualify the missing scopes before choosing the bounded mixed-source pilot versus the learning pilot. Compilation, continuous residency peaks, streaming consumers and sustained lifetime remain outside this gate.
