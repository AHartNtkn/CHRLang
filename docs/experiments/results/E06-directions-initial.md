# E06: operation contracts for richer graph targets

The immediate comparison is about traffic needed for data comparison, table
lookup, binding, occurs traversal and service return. Source OR remains explicit;
no backend race is interpreted as a source search branch.

Sato's nested-pattern system compiles eligible nested matching into ordinary
active-pair rules through auxiliary agents. Its restrictions and conservative
translation are described in §§3–4. This suggests an ablation eliminating the
intermediate controller between inspecting two constructor roots, with both
inspection cost and matching eligibility charged. It does not itself replace a
binding table. [Primary paper](https://arxiv.org/html/2410.00540v1)

Mazza's thesis introduces multiport systems as a concurrent extension and develops
process encodings in Chapters 4–5. Multiple ready ports require an explicit account
of competing interactions; the ordinary single-principal-port argument cannot
simply be reused. [Author thesis](https://www.lipn.fr/~mazza/papers/Thesis.pdf)

For this project's service, a concrete multiport variant can rendezvous on both
operands before comparing their roots. It could avoid the saved-left-root
controller. Pending results must remain linear endpoints, so it cannot consume
one operand for two comparisons without a copying/sharing protocol. This is a
feasible distinct implementation probe, still open. It need not change the source
language: internal deterministic comparisons can be isolated from occurrence races.

The inspected Matsuoka 1999 institutional abstract explicitly includes first-order
unification variables and reports nonconfluence for its extension. That supplies
a lead, not a finite-tree transactional service implementation. A 2026-09-07
follow-up retrieved the indexed [2001 conference abstract](https://contraintes.inria.fr/jfplc2001/resumes.html),
which claims local confluence and an encoding of additive proof nets and lists
guarded unification as a keyword. Direct page retrieval still failed; the full rule
system was not obtained. The abstract does not specify its unification protocol or
the restrictions securing the claim. Do not infer that either system supplies this project's
search semantics or occurs check. [Institutional record](https://ipsj.ixsq.nii.ac.jp/records/17012)

The Uppsala project description identifies fusion as a calculus unifying names
and links work on graphical representations of solos. Name identification is a
possible alias-routing mechanism, not by itself finite-tree constructor unification.
[Research group description](https://www.it.uu.se/research/group/concurrency/basic/fusion.html)

A concrete project-derived fusion probe would give each logical-variable class a
routed cell, merge aliases by redirecting class representatives, and retain
constructor bindings under a serialized transactional request. It could avoid
encoded association-list scans. It still owes an occurs traversal, rollback or
private effects on failure, and branch-local identities. Implementing this protocol
as an operation probe is feasible; no inaccessible historical theorem is needed
to begin. Concurrency and source integration remain separate obligations. This is
our proposed protocol, not a claim that the cited fusion calculus implements it.

For additive proof-net proposals, no separately specified operation protocol has
yet been derived that avoids additional traffic beyond these routing or matching
mechanisms. Inspect a concrete rule system when identifying such a mechanism;
this assessment does not close the broader direction. Likewise none of the first
ordinary-net data tests settles sharing across alternatives, HVM normalization,
dynamic label correspondence, or realistic synthesis.
