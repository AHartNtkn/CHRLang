# First-cycle feasibility: move to the direct-graph question

**Direct graph execution is the next selected architectural investigation.** S01 now has working direct and retained controls, but its current all-pairs source makes every pair a required output. Another key-only timing grid has less immediate decision value than testing an organization that has not received a complete direct trial.

This is a source-grounded readiness assessment plus targeted executable checks. It does not estimate engineering time precisely, rank architectures, or resolve the unimplemented designs. The prior goal turn made progress by implementing incident pair maintenance and validating it against independent expected answers.

## New S03 source gate

The [prospective entry](../registrations/S03-dynamic-resource-source-gate.md) and [executable source/oracle](../../../research/chr-direct-conditional/tests/direct_graph_entry.rs) establish a common correctness target before a direct graph is implemented.

The source recursively generates finite words through explicit OR. A token is observed once by propagation and then consumed with a task. The complete answer contains the generated values twice and the shared unknown token payload twice, with that same unknown in the earlier observation. A second invocation must generate independent words; repeated use of one result must remain correlated. A rejection rule can fail after output-shaped data exists, so publication must await all active obligations.

Expected words and their raw multiplicities are generated mathematically, independently of either executor. Binary, equal-arm and nested three-way choices distinguish fresh recursive births, duplicates and inactive labels. The two-call case is a Cartesian product; the one-call repeated-output case is not. Ground results alone cannot satisfy the full checks because the joint unknown alias and residual multiset are also compared.

Twenty-eight finite configurations produce 290 expected raw answers per executor per run. Both the independent owned-syntax scalar executor and Conditional match them. Preparation is reused across changing queries, and token-first/token-last query insertion is covered. The largest nested two-call case returns 81 raw answers. Equal binary arms at depth three return eight raw copies, while nested three-way choices at depth two return nine histories, not sixteen unconditional label assignments.

A separate continuing-sibling witness returns its one finite nonground answer within the registered service budget without reporting global exhaustion. Negative checks distinguish lost observations, changed aliases and a word that must be rejected. Default, fresh replay and counter-free runs pass all three test functions; focused strict Clippy passes in both configurations. [Validation commands/hashes](s03-source-gate/validation.json), [default](s03-source-gate/default.log), [replay](s03-source-gate/replay.log), [counter-free](s03-source-gate/off.log).

This gate demonstrates comparator capability. It does not implement direct graphs, prove general CHR correspondence, or establish a sharing speedup. The current token is consumed once in every successful branch; it does not yet test competing consumers whose eligibility changes by context. Late-context arrival and cycle/clash equality need additional gates before a graph cost comparison.

## Why this next task, rather than more S01 work

The strongest ready alternative is a native lifecycle comparison of S01's checked lowerings, including sparse/broad updates. That would quantify actual heap and elapsed tradeoffs, which remain open. However, current counts already establish that direct enumeration performs one pair visit per required receipt. The remaining distinction is predominantly representation/maintenance cost on this family; a selective structural/update source is needed before generalizing it to retained matching.

S03 can change where computation, correlation and source effects live. It has a working comparator and now an independent compound gate, so entry no longer depends on preparing those from scratch. Its next correspondence work has greater expected architectural value than enlarging the all-pairs grid. This is a prioritization judgment grounded in concrete readiness and missing mechanisms, not a claim that graphs will win or that S01 is resolved.

S02's context-local integration and S06's richer compiler remain strong alternatives. S09 has a feasible implementation path, but answers a narrower deployment/lifetime question. None requires owner input to continue investigation. Reassess after the direct graph's first resource/provenance gate; do not keep elaborating a favorable fragment while these alternatives remain untested.

## S03 implementation boundary

The next candidate must represent named choices and shared continuations directly. A branch-copy executor with a graph-shaped wrapper does not test the claim. Likewise, compiling this word generator into a graph cannot alone establish general resource-sensitive graph execution: a checked graphless direct generator is then a necessary control, and the eliminated source machinery must not be credited to graph sharing.

Start with a written interpretation of graph nodes, dynamic births, logical variable handles, occurrence identities, consumption and completion. Relate each service operation to permitted source transitions or a semantics-preserving administrative step. Make the finite-yield boundary explicit without assuming that a backend constructor suspends normalization. Require a conflicting-consumer witness, late-arriving context and disconnected failure before selecting cost workloads. Preserve complete answers and raw multiplicity through the same independent gate.

The current untracked choice-graph and HVM files remain unrelated work. No implementation or semantic claim is taken from their presence. The new candidate's code location and ownership will be explicit in its implementation task.
