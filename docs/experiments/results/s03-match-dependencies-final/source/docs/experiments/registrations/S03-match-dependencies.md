# Registered pure-match dependency control

The [pull-tab work attribution](../results/S03-pulltab-work.md) found a certificate asymmetry: copied calls expose constructor arguments that qualify for birth-context reuse, while ordinary indirect arguments do not. This package tests whether ordinary demand can recover that reuse by recording the dependencies of a successful pure match. It is selected ahead of lifecycle timing and reusable lowered-query artifacts because it could change the interpretation of the measured expansion gain.

Add an explicit MatchDependencies policy alongside the existing controls. Only predicates already certified transitively pure and choice-free may widen validity. Begin with the call's birth support. For constructor patterns, follow only already available aliases and cached producer results; include every traversed result's support, every inspected choice selection and that choice's birth support. Recurse into the constructor fields actually inspected by the pattern. Variable patterns retain their graph pointers without demanding them. Do not widen if the required evidence is unavailable. Nonoverlapping, linear source heads remain required; failed clauses supply no reuse result. Resource-consuming, resource-posting and choice-producing definitions retain full current-context validity.

Correctness gates must distinguish dropping unrelated choices from dropping necessary choices, respect conditional producer results and call birth, preserve opaque values and independent dynamic births, and exclude source effects. Compare complete answers independently through the existing source suite, both with and without local pull-tabbing. Structural tests must inspect the support on the retained result, not merely the policy label. No reference-interpreter changes are authorized by this experiment.

After correctness, repeat the registered 72-configuration pull-tab work matrix with MatchDependencies validity, twice, using the same 100,000-tick/200,000-scalar-step and 60-second/1-GiB bounds. Compare expansion counts and graph ownership with the frozen StaticBirth and CurrentContext rows. Record dependency-inspection entries separately under work-diagnostics; they are not force entries or elapsed time. A source mismatch requires repair or an explicit semantic-policy analysis before measurement claims. If equivalent reuse is obtained without copying calls, carry that control into lifecycle registration; if not, identify the remaining dependency or representation difference before ranking architectures.

## Registered lift-support repair

The dependency-policy run shows 140 ordinary versus 162 lifted expansions on four independent depth-32 producers. Inspection shows a second asymmetry: copied calls inherit the full rewrite context even when the argument edge is valid under fewer choices. Before treating this as a graph cost, test a dependency-supported lift under MatchDependencies policy. Start with the original call's birth, include every traversed producer result's support and every already selected choice/birth; include the unresolved target choice's birth without selecting it. The two copies add only their own target selection. Keep the original policies unchanged for attribution. Check structural support, source effects and finite service; repeat the same two diagnostic runs and bounds if the gate passes. Resource effects themselves remain current-context operations. This tests validity of the administrative graph transformation, not reuse of consumption.
