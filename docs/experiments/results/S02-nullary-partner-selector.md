## What the source check permits

Every head use of a selected predicate must lead a rule with no kept heads. The rule has either one removed head or exactly two, with a distinct arity-zero second predicate. The check uses predicate signatures, not fixture names. Same names with different arities remain distinct predicates.

The existing register plan matches the leading occurrence and checks guards. The selector obtains the oldest live nullary partner directly. A nullary partner cannot bind pattern variables or change guard truth, and the distinct signature prevents selecting the same occurrence twice. Both occurrence IDs enter the existing consuming commit in source head order. Since both occurrences are consumed, repeating the same tuple cannot require propagation history.

Missing resources end selection before candidate matching. Later source work can supply a resource and enable the rule. The existing executor still owns the complete body, including fresh variables, alternatives and failure; body effects do not expose a new rule-selection boundary.

The checker rejects non-nullary partners, same-signature pairs, extra heads, kept heads and selected predicates used as partners elsewhere. Specialized execution continues to require Global policy. This is a bounded source optimization, not a general multihead implementation or a language restriction.
