# Confirm repaired derivations against complete execution controls

The [paired attribution](../results/S03-shared-template-attribution.md) establishes that immutable shared compiler terms remove consequential copying costs. This confirmation asks whether fresh-derivation reuse now changes the comparison with ordinary demand, compiled execution and direct source elimination. It is selected before broader integration and reusable lowering because the implementation repair can reverse a ready but still unconfirmed cross-engine comparison. After this package, review breadth before further template refinement.

## Hypotheses and scope

H1: substantial recursive work can repay query-local specialization, including single and distinct requests after the copying repair. H2: repeated requests and independent choices may benefit differently from the same cache. H3: shallow work and complete output construction can favor ordinary or compiled execution. H4: exact source elimination may remain stronger, motivating general source-derived lowering rather than a template architecture conclusion.

Use the existing independent source/scalar gate, all six modes (`dependencies`, `templates`, `scan`, `indexed`, `sealed`, `lowered`) and five families (`single`, `repeat`, `distinct`, `choice`, `grow`). Each configuration crosses depth zero or 32 (grow zero or 12), one/eight changing queries, resource absence/presence and both starting orders: **80 source configurations, 480 engine cells**. Reused queries alternate depth n/n+1 and query key/order. Resource cases have sufficient finishing tokens for policy-independent complete outcomes. The contested-scheduling counterexample is not a timing configuration.

`lowered` is the exact-schema control, not a general compiler. Templates require ground keys and retain ordinary obligations at resource/producer, construction and followed-call boundaries. This experiment does not establish costs for unknown-input derivations, reusable cross-query templates, arbitrary recursion, sustained streams or native compilation.

## Measurement and interpretation

Primary total includes preparation, each setup, execution with complete observation, engine and answer disposal, and prepared disposal. Record source/input-inclusive total, first answer, phase timings, requested allocation traffic and peak requested growth. Queries reuse prepared rules; templates remain query-owned. Ordinary timing has engine/kernel/observer/traversal counters disabled. Meter builds measure requested allocations, not RSS. Native compilation is excluded, so no total compilation-lifecycle superiority is claimed.

For each source configuration compare templates/dependencies, templates/scan, templates/indexed, templates/sealed, lowered/templates and lowered/sealed. Compute the geometric mean of seven within-block primary ratios. Use pointwise 95% percentile bootstrap intervals with 10,000 resamples, seed `7132 + 6 * configuration_index + contrast_index`. Upper bound below 0.90 means a practical gain for the numerator; lower bound above 1.10 means a practical loss; otherwise unresolved. These are pointwise descriptive classifications, not simultaneous or population-wide claims. Retain every configuration and contrary case; use no workload weights.

Investigate material preparation, output or allocation costs before attributing them to the architecture. Treat overlap as uncertainty. Further precision is warranted only if its plausible resolution changes a bounded decision; a mechanism never exercised stays unanswered. Carry distinct favorable regimes into complete-architecture work, and compare any proposed combination against a simpler organization. After the result, explicitly reconsider broader integration, reusable lowering, unknown-input derivations and sustained lifetime rather than automatically refining this source family again.
