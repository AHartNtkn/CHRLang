# Demand execution now supports nonground passive body posts

Nonground passive body posts now preserve delayed values, fresh aliases and consuming effects in the checked demand fragment. The source gate also exposed and repaired a stack overflow in completed-call traversal. These results broaden the candidate's demonstrated capability; they do not establish a performance advantage.

**The next package measures ownership and work on this new capability.** Direct integrated execution remains the strongest distinct alternative. More source extensions are not prerequisites for pricing the supported cases.

## What the extension requires

A posted resource must refer to the same variables as the rest of its application. Posts now carry the same parameterized term representation as call arguments. Source expansion and reusable derivation templates instantiate them through their existing variable environments. Reusing a template can therefore share the plan while preserving fresh runtime variables for each application.

A post can refer to the output that its enclosing call has yet to define. Such plans now contain an explicit local output binder. It reserves a reference before the body expands, then links that reference to the body's contextual result. The binder is generated only when a post mentions that call's output. It adds a graph reference and a linking obligation; its memory and execution costs need measurement.

The ground-only admission restriction is no longer needed for these posts. Call-output writers and passive resource signatures remain distinct. Writable primary output occurrences in resource heads, overlapping call clauses and broader dynamic-call eligibility remain separate unresolved capabilities. This experiment does not adopt a language restriction or replace the current source semantics with a logical-set interpretation.

## Independent source evidence

The new [source suite](../../../research/chr-direct-conditional/tests/nonground_posts.rs) states analytical full answers and checks the scalar executor and the existing inferred-specialization/Indexed executor. Demand runs all three successful-result policies, with every combination of miss reuse, local pull-tabs and derivation templates. Each preparation runs both query arrival orders. Cancellation after one and four service steps precedes complete reuse; retained outputs are checked after their producers and preparation are dropped.

| Source obligation | What the test establishes |
|---|---|
| Delayed input and forward producer | A resource posted before its value is available later matches and is consumed. A post before the producing call retains the same variable. |
| Posted enclosing output | A post refers to the call's eventual result, rather than an unrelated fresh unknown. |
| Fresh local aliases | Two fields and the returned constructor share one variable within an application; repeated calls retain distinct fresh variables. Template-enabled diagnostic cases require actual template hits. |
| Choice and failed branch | A failing branch's posted resource cannot supply a successful sibling; the complete answer multiset is preserved. |
| Competing consumers | One posted occurrence is claimed once; two occurrences can supply two consumers. Remaining occurrences are observed. |
| Hidden constructor cycle | Failure mediated through a posted output is detected even when the query observes no output variables. |
| Constructed posts | Nested constructors and repeated delayed input variables preserve structure and aliasing. |
| Finite sibling beside recursion | The finite posted answer is published while the recursive sibling continues, without reporting exhaustion, across all eight demand option combinations. |
| Continuing calls without posts | The traversal repair also handles the corresponding ordinary continuing call through the same 2,000-step boundary. |

Nine tests cover these obligations. The complete finite cases use a 200,000-service-step cutoff; the continuing cases deliberately remain unfinished after2,000 steps. Their expected finite answer is also checked through explicit specialized/Indexed execution. The progress observation is bounded evidence, not a claim that the recursive branch finishes.

The initial four finite tests failed at the ground-only admission check. After extending the plan, the finite cases passed. The larger progress gate then failed with stack overflow; a no-post control reproduced that failure. These failures and subsequent test output are retained in [the run directory](s03-nonground-posts/).

## The progress defect and its repair

Completed call results formed a chain that `force` followed recursively. The failing posted-source run reached at least700 service steps before overflowing the test thread's stack. An ordinary self-recursive call without posts also overflowed. Increasing the host stack or shortening the progress test would not repair that traversal.

`force` now follows completed results, aliases and selected choices iteratively. Active-call guards and recursive-probe flags remain live along that traversal and are restored when it returns. Actual source dependency evaluation still uses the existing call machinery. The change preserves the distinction between a recursive unresolved dependency and a completed cyclic equality.

Both 2,000-step progress cases pass. The diagnostic source suites and existing demand kernel tests also pass, including recursion, alias-cycle, miss-validity and template work assertions. This establishes the repair for completed-result traversal. It does not establish arbitrary-depth safety for every operation: constructor validation and term normalization still contain recursive traversals. Longer histories, memory growth and complete per-step cost remain required investigations.

## What the result changes

**Demand execution has a broader credible source boundary.** Groundness of passive body posts is not necessary for the qualified fragment. Delayed input references, local unknowns, constructed terms and enclosing outputs can be represented without a second executor. The new output binder and consistently instantiated post terms account for the missing identity relationships.

**Its added responsibilities are concrete.** The candidate must retain context-valid resource births and claims, preserve fresh template variables, connect posted output references, and validate completed equations. Iterative result following avoids host-stack growth from that traversal but does not eliminate repeated traversal or retained history. Those costs must be charged against competent explicit execution.

**No lifecycle or speed selection follows.** These are semantic, ownership-validity and bounded-progress tests. They do not measure allocated bytes, RSS, sustained memory, compilation or counter-free comparative runtime. Existing timing receipts continue to describe their frozen implementations; they must not be presented as timings of this extension.

The existing [dependency ownership runner](../../../research/chr-direct-conditional/examples/dependency_ownership.rs) supplies preparation, cancellation and disposal structure; the new cases exercise a capability it has not priced. Direct integration could change a larger boundary, but first requires a distinct consuming implementation. This is an ordering judgment, not evidence against integration.

At the selected package's boundary, compare finishing a consequential demand cost contrast with direct integration and intermediate joins. Reconsider unresolved recorded-read timing if a complete-path choice depends on it. Additional writable-head or dynamic-choice features do not automatically precede that review.
