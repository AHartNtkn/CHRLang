# E01 v2 result: snapshot storage does not remove repeated execution

All 278 isolated runs passed their expected answers, raw success counts and completion status: the 64 E00 cases and 75 carry cases, each in two snapshot modes. A fresh-process replay reproduced every non-time field, including allocator counters. The persistent mode saves snapshot allocations while preserving exactly the independent source execution being controlled.

## Evidence

- Source/registration/runner commit: `75564e2`; engine implementation first frozen at `a8aa159`.
- Registration: [E01 v2](../registrations/E01.md).
- Raw formal observations: [isolated batch](E01-storage-isolated.tsv) and [isolated replay](E01-storage-isolated-replay.tsv).
- Commands: `cargo build --release -p chr-persistent --example batch`, then `python3 research/chr-persistent/run_batch.py <result-path>` for each batch.
- Environment: rustc 1.97.1, cargo 1.97.1, Linux 6.8.0-138-generic x86_64. One process per case/configuration, 60-second process bound. Elapsed fields are diagnostic only.
- Validation: 56 workspace tests pass, including persistent-map snapshot/range/model checks, transactional unification rollback, simpagation and ordered histories; Clippy with warnings denied and formatting pass.

The retained `E01-storage.tsv` and replay are exploratory single-process batches. Review identified their process-isolation mismatch with the intended registration, so the runner was corrected and the entire formal batch rerun. The formal receipt uses the isolated files.

## Findings

With 256 alternatives, 256 carry expansions and 128 unrelated occurrences, both modes perform 65,791 applications: 255 choice applications plus 65,536 carry applications. Persistent mode creates 1,426,029 map nodes; copy mode creates 1,462,502, including 36,473 snapshot copies. Requested allocation payload falls from 365,331,710 bytes to 362,703,614 bytes. These are storage savings, not common expansion reuse.

For that same case, peak live allocation above the measured baseline is exactly 211,597,174 bytes in both modes. The final live increment is 211,561,550 bytes. Absolute readings differ by six bytes because the two mode argument strings have different lengths; the baseline accounts for this. The no-choice control has identical work and allocation increments across modes.

Output materialization dominates this largest probe's retained memory. At completion the frontier is empty and the immutable term arena contains only 260 nodes, while the engine and caller each retain 256 full residual answers containing the unrelated unary terms. Even W=0 has a peak increment of 211,545,428 bytes. This is a concrete reason to investigate exact shared output representation/stream retention in E14/E15, not a reason to omit residual constraints or change their meaning.

The SK ignored-hole case shows a different balance. Persistent mode requests 519,967 allocation bytes versus 898,647 for copied snapshots. Its peak increment is 164,375 bytes versus 184,303. Both return the same nonground hole restriction and execute 32 applications. Ground duplication similarly preserves its 19 applications while avoiding 3,867 snapshot-node copies. These small application cases establish a real storage opportunity, not a representative speed ranking.

## Scope and next experiments

This control uses predicate-indexed matching, interned terms and an independent exact observer in both modes. Its difference from the reference also includes indexing, unification and observation engineering, so cross-engine timings cannot isolate storage. The within-engine snapshot ablation is the comparison supporting the findings above.

The first control is ready for E03/E04/E05 mechanism comparisons. E01 remains open for trailing/replay, snapshot interval policies, arena reclamation, larger alias/failure workloads, retained-versus-resident memory and statistically supported timing. E14/E15 gain a concrete output-retention question. None of those follow-ups blocks the first conditional finite-support probe, and this result selects no production architecture.
