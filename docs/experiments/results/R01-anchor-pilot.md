# R01 anchor information: a materially stronger dedicated control

Using the active occurrence's known pattern before partner enumeration materially reduces selective-chain work. At size 64, generated active indexed chain lifecycle falls to roughly one third of the before control. This establishes a better conventional control for R02; it does not select a full language architecture.

The [registered comparison](../registrations/R01-anchor-pilot.md) completed all 1,120 processes and 4,480 full answers. Application counts agree between variants. Every metered process has stable post-answer requested live bytes across four changed queries. The [raw evidence](R01-anchor-pilot/raw.jsonl), [all-cell summary](R01-anchor-pilot/summary.tsv), [source and binary freeze](R01-anchor-pilot/freeze.json), [run order](R01-anchor-pilot/order.json) and [independent review](R01-anchor-pilot/review.md) preserve those claims. `research/chr-compiled/experiments/analyze_anchor.py` regenerates and checks the summary.

## The correction and its validation

A later active head is now matched into a local rule frame before earlier partners are enumerated. This makes its established ground key available to the existing index. Query bindings remain unchanged; source occurrence order, resource positions and candidate enumeration order remain intact. A failed pre-match finishes that anchored search only. A successful pre-match yields before another candidate is visited, preserving bounded suspension.

Generic execution uses its pattern evaluator for the pre-match. Generated execution emits corresponding constructor and slot checks directly; it does not call the generic pattern evaluator. First-head anchors need no preliminary match. The extra state is one initialization flag per cursor and an initial populated frame; no new global index or dependency structure is introduced.

The new discovery regression failed before the change and passes afterward. Default and counter-free tests cover independent full observations, legal source commits and terminal checks, candidate-boundary resume, unknown structure, repeated slots, both arrival orders and duplicate consumption. Workspace tests, Clippy and formatting are recorded alongside the focused logs. The source reference interpreter is unchanged.

## Results

Generated active indexed execution, size 64. Lifecycle is the median for preparation plus four queries and all measured disposal, excluding native compilation and separately recorded harness work:

| Family | Before lifecycle (ms) | After lifecycle (ms) | Candidate visits before → after | Execution allocations before → after |
|---|---:|---:|---:|---:|
| Flat chain | 7.023 | 2.309 | 16,838 → 772 | 56,975 → 9,353 |
| Delayed chain | 7.272 | 3.673 | 13,126 → 1,091 | 50,677 → 14,633 |
| Equal-key collision | 0.655 | 0.705 | 391 → 519 | 3,249 → 3,889 |
| Recursive build | 1.385 | 1.440 | 129 → 129 | 11,863 → 11,863 |
| Low-yield repair | 1.301 | 1.288 | 192 → 192 | 4,570 → 4,570 |

The chain and delayed-chain lifecycle ranges do not overlap. The collision, build and repair ranges overlap, so their timing differences do not establish direction under the registered screen. Collision nevertheless shows exact extra traversal and allocation work: known anchor information cannot prune an equal-key bucket.

The corrected active indexed chain visits 100 candidates at n=8 and 772 at n=64; delayed visits 139 and 1,091. This observed range is consistent with linear discovery for these fixtures, unlike the earlier substantial repeated scan burden. It is not a general complexity theorem. Active scanning improves too, but its size-64 chain lifecycle remains 5.155 ms because earlier partner pools still require enumeration.

Global controls retain identical candidate and allocation counts, with overlapping before/after timing ranges. Native compilation units include an additional adverse semantic fixture, so small unchanged-control timing differences can reflect code layout as well as noise. Requested heap allocations are not RSS. Work counters are cumulative through first observation; the allocation column is specifically the execution interval.

## Architectural disposition and next selection

Retain the corrected anchor-aware matcher as the dedicated experimental control. This resolves the discovered unavailable-key cost without changing source semantics. Neither universal indexing nor unconditional pre-matching is proved optimal: the build/repair maintenance costs and equal-key counterpressure remain useful evidence for later access planning.

Select R02's integrated class/constructor and consuming-rule path next. It can change the representation responsible for equality, matching, wakeup and source effects together. Its existing consuming entry and partial-equality serialization analysis specify the semantic obligations. The stronger dedicated control now prevents a representation comparison from receiving credit merely for avoiding the demonstrated scan defect.

The strongest ready alternative is selective index construction/pre-matching based on available keys. It could eliminate known adverse overhead with modest machinery, but currently refines one access strategy; it is less likely than R02 to change the broader representation boundary. Isolated compilation cost remains necessary before any generated-code adoption claim, but these pilots do not make such a claim. R04 solving and R03 search organizations remain independent unresolved directions, not rejected candidates. Reassess priorities after R02's semantic path and bounded cost contrast.
