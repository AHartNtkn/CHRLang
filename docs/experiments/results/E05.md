# E05: named service work and projected storage are separate costs

The first-order family service passes all 240 v1 runs and all 360 v2 runs, with exact non-time replay for each batch. Demand-driven equality preserves correlated choices and can bind an unresolved acyclic family without distributing it. An explicit supported-partition control confirms that eager projection can reduce equation work through structural sharing while still paying substantial construction costs.

## Evidence and validation

Registration: [E05](../registrations/E05.md). V1 freeze: `5682f7a`; v2 supported-partition freeze: `071b38d`. Results: [v1](E05-family.tsv), [v1 replay](E05-family-replay.tsv), [v2](E05-family-v2.tsv), [v2 replay](E05-family-v2-replay.tsv). Build with `cargo build --release -p chr-family --example family_probe`; run `python3 research/chr-family/run_batch.py <output-path>` twice. V2 runs 120 frozen requests in Eager, Named and Partitioned modes. Each process has a 60-second bound and one million finite service steps. Timing is diagnostic.

All 73 workspace tests, Clippy with warnings denied and formatting pass. The service's five tests include 144 generated requests under four assignments, checked against 576 independent reference executions. With three modes, this gives 1,728 assignment comparisons, including MGU variable relationships and branch-local finite-tree failure. The test AST projects independently of the candidate's projection code. Observation of an unfinished request is rejected. All v1 registered equation-count predictions and all measured allocation phase sums hold; v2 preserves the Eager/Named equation counts.

The runtime is a frozen equality service, not a CHR engine. Every listed label is independently active at request birth. No source program can inspect internal choices. Dynamic label births, occurrence/history effects and complete CHR scheduling are not established by these results.

## Named service results

In v2's k=8, W=256 opaque-binding request, Named performs one equation pair and retains one solution region, covering 256 raw and distinct answers. Solver construction/execution requests 11,616 allocation bytes; full observation requests 3,490,480 bytes. Eager performs 256 pairs and requests 6,450,648 solver bytes. Avoiding distribution is a service gain; extraction still materializes all answers.

For the common-prefix request, Named performs 265 pairs versus Eager's 67,840. Solver requests are 12,536 versus 10,341,480 bytes; total requests including construction and extraction are 486,926 versus 10,834,302. This controlled request demonstrates shared structural work before discrimination. It does not establish whole-engine throughput.

The branch-local cycle request performs three Named pairs, keeping one successful region and one failed region. It returns 128 raw successes and one distinct answer, correctly accounting for seven irrelevant active decisions. Solver allocation is 16,432 bytes; observation is 1,691,912 bytes. A failure in one alternative does not reject its sibling or justify omitting its active assignment multiplicity.

## Stronger control and contrary evidence

Partitioned eagerly projects operands with memoization and structural interning, then groups identical equation lists under exact finite assignment supports. Raw variable handles are part of the key. It shares projected storage and equivalent requests without relying on approximate answer equality.

For the k=8, W=256 correlated request, Partitioned performs only 256 equation pairs, versus Named's 1,022 and Eager's 67,840. Interning makes each pair pointer-identical. Yet Partitioned requests 22,386,154 solver allocation bytes, versus Named's 135,096: constructing projected nodes, lookup structures and partitions dominates its smaller equation count. It allocates 65,794 projected nodes and performs 131,616 interning lookups. Counting unification pairs alone would give the wrong cost impression.

The cycle request has only two distinct projected equation lists. Partitioned retains two groups and processes two pairs, reducing solver allocation from Eager's 3,235,304 bytes to 104,004. That is a real exact-partition opportunity. It still exceeds Named's 16,432 solver bytes, and its explicit support/output processing requests 1,813,768 observation bytes. These are finite-set implementation costs, not a rejection of compressed partitions.

For the opaque request, all 256 projected terms differ. Partitioning retains 256 groups and requests 19,412,706 solver bytes despite sharing some nodes, versus Eager's 6,450,648 and Named's 11,616. The no-choice k=0, W=0 control also exposes overhead: total requests are 5,034 bytes for Partitioned, 2,343 for Eager and 2,212 for Named. Interning and grouping are not free improvements.

V2 adds an optional finite support field to the shared context structure, so use v2's within-version allocation comparisons. V1 remains a reproducible distribution ablation, not the allocation authority for comparing against Partitioned.

## Disposition and follow-ups

The first E05 service probe is complete; the direction remains open. Dynamic choice lineage and effect correlation must be implemented before a full CHR claim. Large alias graphs, resumable occurs/projection work, compressed support sets, canonical symbolic DAGs and output extraction remain feasible investigations. The correlated case specifically motivates comparing symbolic structural equivalence before eager projection; it does not prove that doing so is always profitable. Reference/generated checks remain bounded and do not replace a general preservation argument.

The next first probe is E07 delayed splitting. It investigates where delaying source disjunction, rather than only equality demand, saves work or causes speculation. Further refinement of E05 need not precede it. No language or production architecture decision has been adopted.
